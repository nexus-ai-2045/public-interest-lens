# フィードバックループ（5段）

更新日：2026-10-29。小さいループほど速く回り、上の段ほど「ループそのもの」を直す。各段に「何を測るか」「どこに記録するか」「何を直すか」「改善の選択肢」を置く。改善の選択肢は、いま採っていない手も消さずに残す。回せる状態かは `python3 scripts/loop_status.py` で測る（L5）。

## 各段の詳細

### L1 変更
- 測る：事前チェックの成否、個人名義検査の成否、触った範囲のテスト。
- 新しいクラウドのセッションは、最初に `python3 scripts/install_hooks.py` を回す（git フックと固定版 gitleaks を入れる。preflight の「フック」が確かめる）。prepare-commit-msg が Claude の共著者行・セッション行を自動で取り除き、commit-msg・pre-push が repo-preflight の名義検査を回す。GitHub の API 経由のコミット（push_files など）と PR 本文にはフックが効かないので、付けない。
- 新しいクラウドのセッションは git の作者名義が未設定で「コミット名義」「個人名義」が失敗する。コミット名義を `nexus_ai`・GitHub の noreply にしてから回す（値の中身は出さない、AGENTS.md）。
- 派生ファイル（members.json・配布 distribution）に頼るテストは、先に `node scripts/build_public_members.mjs` と `python -m scripts.build_public_distribution …` が要る。作っていないと `npm test`・unittest が赤に見える。順番は CI と同じなので、`local_verify.py` を使えば迷わない。
- 改善の選択肢：遅いテストに印を付けて分ける／pre-commit フックにする（`--no-verify` は使わない）。

### L2 PR
- 測る：CI の成否、レビューの指摘数、`roadmap_check.py` の残り件数。
- GitHub Actions は課金不足で赤になりがち → `local_verify.py` で CI と同じ手順を回し、結果を根拠にする（再実行で待たない）。手順は verify.yml が正本で、この文書やスクリプトに写しを持たない。
- マージ前の定型（並列の PR が多いとき）：`python3 scripts/sync_main.py`（main に rebase。charts.json など生成物だけが衝突したら main 側を取って作り直し、差分が出たら1コミットにする。生成物以外の衝突は中止して知らせる）→ `python3 scripts/local_verify.py` → `git push --force-with-lease` → マージ。PR が main より遅れていると「verify is expected」でマージできないのも、ここで解ける。
- PR 本文は作る前に `python3 scripts/strip_commit_trace.py --body < 本文.md` を通す（プロジェクトスレッドの URL が CI の名義検査で赤になるので、リンクだけ消え、attribution の行と Requested by は残る。フックは API 経由の PR 作成に届かない）。
- マージキュー（GitHub の merge queue）は入れない：キューは待ち行列ごとに CI を回し直すので、課金枠が足りない今は逆に詰まる。順番は上の定型と「マージは1本ずつ、main の最新に載せてから」で守る。枠が戻ったら再検討する（改善の選択肢）。
- 改善の選択肢：同じ指摘が2回出たら検査（テスト）にする。

### L3 マージ後・更新
- 測る：main の `verify`、取得できた取得元の数、再計算した本数、出典チェックで外した本数、額つき・理由つきの本数、2系統の不一致率・第3の判定者の決着率・訂正の採用率。
- 無限ループを防ぐ：失敗した取得はその回は飛ばす（再試行しない）。外した法律は次の回に照合し直すだけ。
- 判断の型の記録：不一致や訂正が出たら、1ファイルに「誤りの型」「件数」「ルールの変更」「変更後の不一致率」を追記する（例 `docs/学習記録/ai-field-v1.md`）。
- 改善の選択肢：取得元の許可（`*.go.jp`、R16）／件数の変化が大きい回は PR を下書きのまま止める／系統2のモデルを替えて独立性を上げる。

### L4 リリース前
- 測る：`release_check.py` の3段（ループの点検・スモークと E2E・CI と同じ検査）がすべて合格か。1つでも失敗なら配信しない。
- 本番への配信はリリース時にまとめて1回（Vercel の回数制限、`docs/operations.md`）。点検は配信しない。
- 改善の選択肢：スモークの画面を増やす／リリース後に公開サイトを開いて版を確かめる段を足す。

### L5 メタ
- 測る：ロードマップの「済」の割合、G1〜G9 の達成数、L1〜L4 のどれかが2週続けて記録なしになっていないか。
- 改善の選択肢：段の周期を変える／記録先を1か所に寄せる／回っていない段を自動化する（定期実行）。
- 測る：`loop_status.py`（5段の入口と記録の置き場所がある、改善の記録が31日以内、ロードマップの検査）、ロードマップの「済」の割合、G1〜G6 の達成数。
- 改善の選択肢：段の周期を変える／記録先を1か所に寄せる／回っていない段を自動化する。
