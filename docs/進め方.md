# 進め方の正本（ルールを1つにまとめた版）

スレッドを始めたら最初に読む。2026-10-31 時点。モデルと effort の細部は [モデルの使い分け](モデルの使い分け.md)、名義・公開・評価の安全は `AGENTS.md` と各 ADR が持つ。このページは、それらを矛盾なく組み合わせるための優先順位と決着だけを書く。

## 1. 優先順位（食い違ったらこの順）

1. ねくの現在の指示（スレッド内の発言）
2. プロジェクト指示（調整役が管理。変更は調整役）
3. このページ
4. [モデルの使い分け](モデルの使い分け.md)（モデル・effort・並行・レビューの詳細）
5. `AGENTS.md`・ADR（名義・公開範囲・評価の安全。緩めない）
6. pstack（Codex から移植中のスキル。参考。採用範囲は 4 章）

## 2. スレッドの一生（これだけ覚える）

1. 開始：`python3 scripts/install_hooks.py`、`python3 scripts/preflight.py`。このページを読む。
2. 依頼を受けたら、目標・完了の判定・見せる証拠・すでに分かっていること・制約の5つを自分の言葉で書き直す（pstack の流儀）。曖昧なら1行で確認の形にして、おすすめで進める。
3. 実行して観察できることは人に聞かない。試して結果で決める。
4. 機械処理はスクリプト。2回以上くり返す処理も scripts/ へ。方針が変わったらリファクタ・ruff・テストを同じ PR か直後の PR で。
5. 実装は Sonnet、大量の短い判定は Haiku、裁定と最終レビューは Opus。
6. 一次検査（ruff・pytest・vitest・build・ロジック検査・preflight）が緑でなければ先へ進まない。
7. 評価・公開データ・計算に触る PR は、Opus medium と Sonnet medium の2系統で見つけ、Opus が絞る。docs と小修正は一次検査だけでよい。
8. マージは自分で。条件は一次検査が緑と、動いたときの自動レビュー指摘が0。自動レビューが上限で動かないときは 6 と 7 で代える。
   - **Claude Code のレビューは毎回回す。** ChatGPT／Codex は待たず、残高があって動くときだけ、大きい PR とリリース前に追加で回す。①手元の検査（preflight --smoke、pytest、ロジック保証、build）②PR ごとにレビュー用スレッドを立て Sonnet で `/code-review`（大きい PR・判断が割れたときだけ Opus が裁定）③CI が課金上限で止まっているリポは①で判断。同じ系統のモデルは見落としが似るので、テストとロジック保証で補う。標準ルールの正本は nexus-ai-skills の `requesting-code-review`。
9. 済んだら resolve。誰かの次の手が残るなら open のまま、待ち先を具体的に書いて調整役へ知らせる。

## 4. pstack と potetomode の扱い

- 「potetomode」は pstack の**作業の入口 `poteto-mode`**（上流の作者は Lauren Tan）。目標を伝えると、プレイブック（バグ修正・機能追加・調査・PR 作成など）に振り分け、手順を ToDo に写して進める。
- 移植物は Mac の `~/.codex/skills/pstack/`（Codex 用）にあり、**このクラウド環境にはスキルが入っていないので `/pstack` は動かない**。動く場所は Codex の `$pstack` か、Claude Code にプラグインとして入れた環境。
- 採用：5要素での依頼、観察で分かることは聞かない、「new task」で切り替え、長い作業の判断ログ（show-me-your-work）、子は新規で起動して報告を鵜呑みにしない、停止線（現在の指示・安全境界を上流スキルで緩めない）。
- 不採用：GPT・Grok の役割表、サブエージェントを増やす既定（約7〜15倍のトークン）、グローバル設定やモデル設定の書き換え、Cursor 専用機能。
- 入れるなら：Claude Code 向けの配布は用意されている（`references/runtime-adapters.md`）。入れる前に、差分と戻し方を出してねくの承認を取る（pstack 自身の停止線と同じ）。

## 5. 完了の定義（リリース前に確認する）

次がそろったら「全データが正しいロジックを通った」と言える。そろうまで配信の話はしない。

1. 評価台帳に、対象の全件（法律3,415本・議員3,001人など）が「額あり」か「額なし＋理由」のどちらかで載っている（`scripts/audit_links.py` と `docs/評価台帳.md`）。
2. `tests/test_evaluation_logic.py` の違反が0。直したら基準を下げ、増やさない。
3. 独立した抜き取り検証（前回は118本中78本不合格、#133）を、同じ方式でやり直し、**不合格0を目標**にする（ねく決定 10-31）。
4. 公開前検査（出典・議員ページ・個人名義）が緑。

直せない不合格は『参考』に下げてよい。ただし**参考値は出し続け、根拠も一緒に出す**（隠さない）。順位に使うのは本線の付加価値だけ、という既存の決めは変えない。

## 6. 認知の罠と収束

- 「ルールが多いほど安全」：多いと読まれない。迷ったら 2章の9行に戻る。
- 「全部をオーケストレーションすれば速い」：依存の強い仕事は1スレッドのほうが速く安い。
- 「報告が来たから済み」：確かめてから採用する。確認できなかった点と探した場所を、子の報告に必須にする。
- 「完了＝リリース」：別の2つ。完了は証拠、配信はねくの合図。
- 新しい思いつきはロードマップに1行。このページは増やさず、矛盾が見つかったら 3章の表の行を直す。
