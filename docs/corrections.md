# 訂正・異議の手順

M3（限定公開）の受入条件「訂正窓口」の正本です。受付は公開の `GitHub` `Issue`（テンプレート「訂正・異議の申し立て」、ラベル `correction`）です。脆弱性・秘密情報は [セキュリティ方針](../SECURITY.md) の窓口へ分けます。

## 画面からの受付

公開サイトの議員ランキング（各議員の欄）と法律ランキング（各行の詳細）に「反論・訂正」ボタンがあります。押すと、対象（名前と画面の URL）と、その画面が使った出典が入った状態で `Issue` の作成画面が開きます。隣の「寄せられた反論・訂正を見る」は、その項目の題名で絞った `correction` の一覧です。

### GitHub アカウントが無い人向け（メール）

公開ビルドの環境変数 `VITE_CORRECTION_EMAIL` に受付用アドレスを入れると、ボタンの隣に「GitHub を使わずメールで送る」が出ます。押すと、件名と本文に対象・画面の出典・書いてほしい欄が入ったメールの下書きが開きます。届いたメールは、個人情報を除いて `correction` の `Issue` に転記し、以降は同じ流れで扱います。変数が空のあいだは、メールの窓口は出ません。

有効にする手順（持ち主の作業、1回だけ）：

1. 運営名義（nexus）の受付専用アドレスを用意する。持ち主の私用アドレスは使わない。
2. Vercel のプロジェクト `public-interest-lens` → Settings → Environment Variables で、`VITE_CORRECTION_EMAIL` にそのアドレスを入れる（Production）。
3. Deployments から最新の本番を Redeploy する。

## 流れ

1. **受付**：`Issue` を受け、個人情報や非公開資料が書かれていれば、その部分を非表示にしてから扱います。
2. **仕分け**：引用・人物の同定・行動記録・反証・判定への異議のどれかに分けます。根拠の出典がなければ、出典を求めて保留します。
3. **確認**：示された出典を、既存の資料登録処理で保存・再読します。申し立てを確認済み事実として扱わず、原本との一致で判断します。
4. **改版**：誤りが確認できたら、政策検証記録を新しい `revisionId` で改版します（設計決定0003）。旧改訂は上書きせず残し、旧改訂への検証を新改訂へ流用しません。
5. **再計算**：同じ入力版の全人物を再計算します（[運用手順](operations.md) の「順位の異議・反証追加」）。判定ルールの変更が必要な異議は、1件の訂正ではなくルールの新版として扱います（設計決定0007 §5）。
6. **回答**：`Issue` に、採否・理由・新しい評価版を記録して閉じます。採らなかった場合も理由を残します。

## 担当

評価責任者が採否を決めます。公開中の評価版を差し替える配信は、通常の公開と同じく人の承認を要します。

## まだ決まっていないこと

- 公開後の応答期限。暫定の目安は、受付の返事（仕分けの結果）を7日以内、採否の回答を30日以内とします。
- メール窓口の受付アドレス（上の手順で有効にするまで、メールの窓口は出ない）。
