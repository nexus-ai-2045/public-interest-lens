# モデルの使い分け（Anthropic 公式のやり方にそろえた版）

スレッドを始めたら最初に読む。2026-10-31 時点。出典は末尾。価格は公式表の値で、変わりうる（採用前に公式の比較表で確認）。

## 1. 30秒版（迷ったらここだけ）

| 仕事 | 使うモデル | effort（考える深さ） |
|---|---|---|
| 機械処理（集計・変換・検査・差分） | モデルを使わない。scripts/ のスクリプト | なし |
| 探索・大量で独立した調査・抽出・整形・決まった検証・小さな修正 | Haiku 5.5（短い仕事を1つずつ、並行） | medium が基本。短い抽出は low、取りこぼすなら high |
| 機能・リファクタ・バグ修正・ふつうのレビュー | Sonnet 5.5（既定） | medium が基本。件数が多い作業は low。難しければ high |
| 難所・性能が効く判断・文章・裁定・最終レビュー | Opus 5.5 | medium（足りなければ high） |
| Opus を high〜xhigh にしても足りない長丁場・深い調査 | Fable 5.1（例外扱い） | high〜xhigh |

- 価格（100万トークンあたり 入力/出力）：Haiku 5.5 $0.10/$0.50、Sonnet 5.5 $2/$10、Opus 5.5 $4/$20、Fable 5.1 $10/$50。
- 上げる順番は「プロンプトを直す → effort を上げる → モデルを上げる」。公式は「effort の調整はモデルを替えるより良い手であることが多い」としている。推論が浅いときは、プロンプトで誘導せず effort を上げる。
- 上位モデルへ上げる根拠は、感覚ではなく20件ほどの実データでの比較（公式：評価セットを作るのが最重要）。
- Fable は既定に入れない。使えるかはその場で確かめ、使えなくても別モデルに黙って置き換えない（置き換えたら報告に書く）。

## 2. モデル別の公式の勧め

- **Haiku 5.5**：最低遅延・最低価格。大量処理、コスト重視、サブエージェント向け。長いエージェント指示を low で渡すと途中で止めたり、確認を飛ばしたりする。だから「短い仕事を1つだけ」が公式にも合う。コードを触らせるなら「実行して確かめてから報告」を指示に入れる。複雑な判断・影響の大きいもの・根拠が足りないもの・品質が落ちたものは Opus に上げる。
- **Sonnet 5.5**：日常の実装・データ分析・ツール利用エージェントの標準。Claude Code の費用ガイドも「ほとんどの実装は Sonnet、Opus は複雑な設計判断と多段の推論だけ」。プロンプトの公式ガイドは Sonnet は medium が基本、件数の多い作業は low、最も難しく長い作業は Opus。
- **Opus 5.5**：複雑なエージェント実装、大規模な改修、長時間の自律作業。API の選択表は「多くの仕事は Opus から始める」だが、Claude Code では Sonnet 既定が公式ガイド。このプロジェクトは費用優先なので Sonnet 既定のままでよい。
- **Fable 5.1**：最高性能。数時間続くエージェント、多段の深い調査。Opus で足りないと評価で分かったときだけ。
- **effort の目安**（公式 Prompting best practices）：max は考えすぎのおそれ。xhigh はコーディングとエージェント作業に最適。high は知能が要る作業の最低ライン。medium はコスト重視。low は短く限られた仕事向け。
- 共通：Opus 5.5・Sonnet 5.5・Haiku 5.5・Fable は考える機能を完全には切れない。軽くしたいときは effort を下げる。
- 安全装置：Opus 5.5 は Fable 並みの安全装置を持ち、フラグが立った依頼は古いモデルに移って続く設定（switchModelsOnFlag）がある。モデルが途中で替わりうるので、重要な結果には使ったモデルを書く。

## 3. 大きな仕事の渡し方（Opus 5.5 公式ブログの要点）

- 仕事は丸ごと渡し、終わりの条件と「いつ止まって聞くか」を書く。「think carefully」のような行は消す（考える量は effort で変える）。
- 長い作業は止まらず進めるルールにし、止まるのは破壊的な操作の前だけ。permission prompt は外さない。
- 監査・移行・大規模レビューはサービスごと（件ごと）に subagent へ分け、返ってきたら証拠を確かめてから採用する。「報告されたこと」と「確かめたこと」を混ぜない。
- タスク一覧は TASKS.md のようなファイルに置き、会話に頼らない。
- 最後の見出しを指定する（例：「ねく待ち／変更／発見」）。調査では「確認できなかった点と、探した場所」を必ず書かせる。

## 4. 並行・委譲のルール（サブエージェント／複数スレッド）

委譲してよい：
- テスト・ログ・検索など出力が多い作業（長い出力は子の中に閉じ、要約だけ返す）。
- 自己完結して、要約で足りる調査。
- 互いに独立した作業（件ごと・ファイルごと）。

委譲しない：
- 単純な作業、順番にやる作業、1ファイルの作業、何度もやり取りが要る作業、計画→実装→テストで同じ文脈を共有する作業。
- 依存関係が多い作業（多くの実装が該当）。複数エージェントは通常チャットの約15倍のトークンを使うので、価値が高く分割できる仕事だけで採算が合う。
- 全体が1つの文脈に収まる仕事は、上位モデルを低 effort で単独で走らせるほうが、公式の測定ではすべての場合で良かった。

運用の決まり：
- 委譲の指示に必ず書く4点：目的／出力の形／使う情報源とツール／作業範囲の境界。規模の目安（単純な確認は1体、比較は2〜4体、大規模調査で初めて10体超）も書く。
- 同時に走らせる数の公式の上限は大きい（既定で20、入れ子3層）が、運用の目安は新規4〜6、修復1〜2。subagent の中からさらに subagent を起動しない。
- 続きは SendMessage で。10分止まった子は失敗するので、長い待ちは作らない。
- 繰り返し使う子は .claude/agents/<name>.md に model・effort・maxTurns・tools・permissionMode・isolation: worktree・background を固定して定義する。呼ぶたびに指定し直さない。

Haiku 並行の運用（このプロジェクトの既定）：
1. 1つの Haiku には短い仕事を1つだけ渡し、終わったら止める。
2. 並行に配り、結果を全部回収してから統合する。取りこぼしは回収漏れとして数える。
3. Haiku の結果は「合格率を測ってから」本番に使う（5章）。

## 5. レビューの段階分け

- 一次：スクリプト（lint・pytest・tests/test_evaluation_logic.py）。落ちたら人間にもモデルにも回さない。
- 二次（見つける段階）：Opus medium と Sonnet medium の2系統を並べて審査する。確信度と重大度を付けて、見つけたものを全部報告させる。絞り込みは次の段階でやる。
- 三次（絞る段階）：割れた分の裁定と最終レビューを Opus が行う。「マージを止めるべき問題だけを挙げ、1件ごとにファイルと行、なぜ間違いか、失敗をどう示せるかを書く」と指示する。公式ブログでは、最低 effort の Opus 5.5 でも high の Opus 5 より多くのバグを少ない誤報で見つけた。人が見る前に必ずこの審査を通す。
- 自己点検は「下書き → 見直し → 直す」の3段に分ける。
- 相談（裁定）が1回も起きない仕事に上位を付けても効果がないので、裁定が実際に何件起きたかを記録する。
- 大量判定に Haiku を使う前に、20件の抜き取りで Sonnet（または自分の正解）と突き合わせ、合格率を決めておく。公式の測定では、Haiku の子を付けた構成は費用を約32%減らす代わりに合格率が約4pt下がり、「Sonnet の low を混ぜた単独」とほぼ同じ結果だった。Haiku は「無料で同じ品質」ではない。

## 6. 公式との食い違いと、おすすめ

| 現行のやり方 | 公式の見方 | おすすめ |
|---|---|---|
| 調整役が全作業をオーケストレーションする | 分割できて高価値な仕事だけ採算が合う。依存の強い作業は単独のほうが良い | 調整役は割り振りと統合に絞る。依存の強い実装は1スレッドに任せ、子を増やさない |
| effort を決めていない | 使い分けの主なレバー | 1章の表の既定を採用。調整役も high 固定にせず、割り振りだけの回は low〜medium |
| 大量判定は Haiku（品質の関門なし） | まず評価、合格率を見て採用 | 20件の抜き取り＋Sonnet 突き合わせを手順に追加（スクリプト化の候補） |
| 審査が1系統になりがち | 見つける段階と絞る段階を分ける。2系統で並べる | Opus medium と Sonnet medium の2系統→Opus が絞る |
| Fable の位置づけがない | Opus で足りないときだけの上位 | 例外枠。使えるか確かめ、黙って置き換えない |
| Opus は裁定と最終レビューだけ | 型は公式と同じ | 裁定の件数を数え、ゼロが続くなら最終レビューも Sonnet に下げる |
| 子の結果をそのまま使う | 返ってきたら証拠を確かめてから採用 | 子の報告に「確認できなかった点と探した場所」を必須にし、抜き取りで再確認する |
| CLAUDE.md・プロジェクト指示が長い | 200行以内、手順はスキルへ。毎回すべてのトークンを払う | 詳しい手順は skills に逃がし、指示は要点だけ |

## 7. 認知の罠

- 「上位モデルなら安心」：品質差を測らずに上げると費用だけ増える。先に effort とプロンプト。
- 「並行にすれば速くて安い」：複数エージェントは約15倍のトークン。独立していない仕事は遅く高くなる。
- 「Haiku で全部回せば安い」：合格率が下がった分の手戻りが費用に出る。完了あたりの費用で見る。
- 「子が報告したから済んだ」：報告は証拠ではない。確かめてから採用する。
- 収束：迷ったら1章の表の「Sonnet・medium・1スレッド」に戻る。例外にする理由は PR か ADR に1行残す。
