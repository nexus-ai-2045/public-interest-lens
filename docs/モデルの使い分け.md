# モデルの使い分け（Anthropic 公式のやり方にそろえた版）

スレッドを始めたら最初に読む。2026-10-31 時点。出典は末尾。価格は公式表の値で、変わりうる（採用前に公式の比較表で確認）。

## 1. 30秒版（迷ったらここだけ）

| 仕事 | 使うモデル | effort（考える深さ） |
|---|---|---|
| 機械処理（集計・変換・検査・差分） | モデルを使わない。scripts/ のスクリプト | なし |
| 大量で独立した単純判定・抽出・要約 | Haiku 5.5（短い仕事を1つずつ、並行） | low〜medium |
| 実装・調査・PR・ふつうのレビュー | Sonnet 5.5（既定） | 既定の high。エージェント実装は medium から試す |
| 判定が割れたときの裁定・最終レビュー・設計判断 | Opus 5.5 | medium〜high |
| Opus を high〜max にしても足りない長丁場・深い調査 | Fable 5.1（例外扱い） | high〜xhigh |

- 価格（100万トークンあたり 入力/出力）：Haiku 5.5 $0.10/$0.50、Sonnet 5.5 $2/$10、Opus 5.5 $4/$20、Fable 5.1 $10/$50。
- 上げる順番は「プロンプトを直す → effort を上げる → モデルを上げる」。公式は「effort の調整はモデルを替えるより良い手であることが多い」としている。
- 上位モデルへ上げる根拠は、感覚ではなく20件ほどの実データでの比較（公式：評価セットを作るのが最重要）。

## 2. モデル別の公式の勧め

- **Haiku 5.5**：最低遅延・最低価格。大量処理、コスト重視、サブエージェント向け。長いエージェント指示を low で渡すと途中で止めたり、確認を飛ばしたりする。だから「短い仕事を1つだけ」が公式にも合う。コードを触らせるなら「実行して確かめてから報告」を指示に入れる。
- **Sonnet 5.5**：日常の実装・データ分析・ツール利用エージェントの標準。Claude Code の費用ガイドも「ほとんどの実装は Sonnet、Opus は複雑な設計判断と多段の推論だけ」。チーム型の並行作業の子も Sonnet を勧めている。
- **Opus 5.5**：複雑なエージェント実装、大規模な改修、長時間の自律作業。API の選択表は「多くの仕事は Opus から始める」だが、Claude Code では Sonnet 既定が公式ガイド。このプロジェクトは費用優先なので Sonnet 既定のままでよい。
- **Fable 5.1**：最高性能。数時間続くエージェント、多段の深い調査。Opus の high〜max でも足りないと評価で分かったときだけ。常用しない。
- 共通：Opus 5.5・Sonnet 5.5・Haiku 5.5・Fable は考える機能を完全には切れない。軽くしたいときは effort を下げる。

## 3. 並行・委譲のルール（サブエージェント／複数スレッド）

委譲してよい：
- テスト・ログ・検索など出力が多い作業（長い出力は子の中に閉じ、要約だけ返す）。
- 自己完結して、要約で足りる調査。
- 互いに独立した作業（件ごと・ファイルごと）。公式の並列上限の既定は20。

委譲しない：
- 何度もやり取りが要る作業、計画→実装→テストで同じ文脈を共有する作業、小さくて速い修正。
- 依存関係が多い作業（多くの実装が該当）。複数エージェントは通常チャットの約15倍のトークンを使うので、価値が高く分割できる仕事だけで採算が合う。
- 全体が1つの文脈に収まる仕事は、上位モデルを低 effort で単独で走らせるほうが、公式の測定ではすべての場合で良かった。

委譲の指示に必ず書く4点：目的／出力の形／使う情報源とツール／作業範囲の境界。規模の目安（単純な確認は1体、比較は2〜4体、大規模調査で初めて10体超）も書く。単純な質問に大量の子を起こすのが公式の失敗例。

Haiku 並行の運用（このプロジェクトの既定）：
1. 1つの Haiku には短い仕事を1つだけ渡し、終わったら止める。
2. 並行に配り、結果を全部回収してから統合する。取りこぼしは回収漏れとして数える。
3. Haiku の結果は「合格率を測ってから」本番に使う（4章）。

## 4. レビューの段階分け

- 一次：スクリプト（lint・pytest・tests/test_evaluation_logic.py）。落ちたら人間にもモデルにも回さない。
- 二次：Haiku か Sonnet が独立した2系統で判定し、割れた分だけ上へ。
- 三次：Opus は割れた分の裁定と最終レビューだけ。公式の「小さいモデルが回し、難しい判断だけ上位に相談」と同じ型。ただし相談が1回も起きない仕事では上位を付けても効果がないので、裁定が実際に何件起きたかを記録する。
- 採点は「基準ごとに 0〜1 と合否」を単一のプロンプトで。人手の確認は自動採点で拾えない例外を見つけるために残す。
- 大量判定に Haiku を使う前に、20件の抜き取りで Sonnet（または自分の正解）と突き合わせ、合格率を決めておく。公式の測定では、Haiku の子を付けた構成は費用を約32%減らす代わりに合格率が約4pt下がり、「Sonnet の low を混ぜた単独」とほぼ同じ結果だった。つまり Haiku は「無料で同じ品質」ではない。

## 5. 公式との食い違いと、おすすめ

| 現行のやり方 | 公式の見方 | おすすめ |
|---|---|---|
| 調整役が全作業をオーケストレーションする | 分割できて高価値な仕事だけ採算が合う。依存の強い作業は単独のほうが良い | 調整役は割り振りと統合に絞る。依存の強い実装は1スレッドに任せ、子を増やさない |
| effort を決めていない | 使い分けの主なレバー | 表の既定を採用。調整役も high 固定にせず、割り振りだけの回は low〜medium |
| 大量判定は Haiku（品質の関門なし） | まず評価、合格率を見て採用 | 20件の抜き取り＋Sonnet 突き合わせを手順に追加（スクリプト化の候補） |
| Fable の位置づけがない | Opus で足りないときだけの上位 | 表の通り例外枠に入れる |
| Opus は裁定と最終レビューだけ | 型は公式と同じ | 裁定の件数を数え、ゼロが続くなら最終レビューも Sonnet に下げる |
| CLAUDE.md・プロジェクト指示が長い | 200行以内、手順はスキルへ。毎回すべてのトークンを払う | 詳しい手順は skills に逃がし、指示は要点だけ |

## 6. 認知の罠

- 「上位モデルなら安心」：品質差を測らずに上げると費用だけ増える。先に effort とプロンプト。
- 「並行にすれば速くて安い」：複数エージェントは約15倍のトークン。独立していない仕事は遅く高くなる。
- 「Haiku で全部回せば安い」：合格率が下がった分の手戻りが費用に出る。完了あたりの費用で見る。
- 収束：迷ったら1章の表の「Sonnet・medium・1スレッド」に戻る。例外にする理由は PR か ADR に1行残す。
