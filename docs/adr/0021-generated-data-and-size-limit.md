# 設計決定0021：生成物の扱いと、1回の変更の大きさの上限

日付：2026-10-29。状態：採用（方針）／移行は別の PR（ねく 2026-10-29「でかい生成物の場合はどうするかをはっきり決めておく」「差分が大きいのは、少しずつ変える方針に反する」「検査は大きさで止めるのは筋違いだが、上限は変えない」）。

## 起きたこと
OECD 表6を取り直した変更（#74）は、法律3,415本中3,085本の数字が動き、足す行が約5.9M文字になって、公開前検査（repo-preflight）の「1回で足す行の上限 4M 文字」に止められた。分けて直すと、旧版の固定（#84）→産業への結び直し（#89）→定例除外の再判定（#91）の3本はどれも4M以下に収まった。原因は変更の大きさではなく、入力の版ずれと、別々の理由の変更を1本にまとめたことだった。

## 決めたこと
1. **ファイルの種類を3つに分ける。**
   - 固定入力（取得した原本の整形表。例：`industry_va.csv`）：Git に入れる。版を固定し、取り直すのは単独の PR にする。
   - 判定の表（AI や人が決めた表。例：`sector-overrides.csv`・`exclusion-overrides.csv`）：Git に入れる。再現できない判断なので正本はここ。
   - 決まった手順で再計算できる派生（`macro.csv`・`laws.json`・`ranking.json`・`charts.json` など）：**Git から外す方向**（下の「移行」）。それまでは Git にあるので、下の手順に従う。
2. **上限は変えない。** 1回の commit・1本の PR で足す行は4M文字まで。大きさで例外を作らず、PR を割って守る。repo-preflight に個別プロジェクトの事情は入れない。
3. **超えるとき（超えそうなとき）の手順。**
   - 入力の版を変えるのは単独の PR。先に旧版で固定して差分を小さく見せ、版上げは別に出す。
   - 別々の理由の変更（入力の固定・判定の表・規則の直し）は別々の PR にする。1つの PR は1つの理由。
   - 各 PR は単独で CI が緑になる順に並べる（前の PR がマージされてから次を出す）。
   - 普段の PR では生成物を大きく動かさない。動いたら、動いた理由（入力か規則か）を PR の本文に書く。
4. **移行（別 PR、この決定の後）。** 生成物を Git から外し、リリース時に固定した入力から一括で作る。CI の試験は「生成した直後の整合」だけを見る（Git にある生成物とのずれを直す作業をなくす）。
5. **speeches.csv（Mac にしかない大きな入力）の扱い。** CSV そのものは Git に入れない。Mac で作った法律の概要（`what`・`aim`・`concern` など）を小さな派生ファイルにして Git に残し、CI・Vercel の生成はそれを読む。概要を作り直すのは Mac で、結果は単独の PR で入れる。

## 限界
- 移行までの間は、生成物が Git にあるので、入力を変えると大きな差分が出る。上の手順で分けて守る。
- 概要の派生ファイルの形（1法律1行）と、生成の入口（リリースの手順）は移行の PR で決める。

## 認知の罠
- 「上限が低いから上げる」：上限は検査の目的ではなく、変更を小さく保つ合図。上げると、版ずれのような原因が隠れる。
- 「まとめたほうが速い」：まとめると、レビューの指摘（今回は4件）の直しのたびに全部が動く。
